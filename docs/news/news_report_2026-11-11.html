8.0/10
Berkeley RDI：Blog（AI 安全与评测） · 2026-11-11 · ↗ 原文 · 📍 Chapter 5, Section II
2026 年 11 月 10 日，UC Berkeley RDI 联合新加坡国立大学、UC Riverside、UC Santa Barbara 发布 CyberBinGym 基准（草案），测试 AI 智能体能否仅凭二进制补丁写出真实漏洞利用。任务构造自 CyberGym 与 OSS-Fuzz、ARVO 工件，重建漏洞版本与补丁版本，移除 sanitizer 插桩、剥离符号与调试信息后得到 604 个已验证二进制对，从中选出 100 个任务，覆盖 53 个开源项目、6 类内存与类型安全错误，漏洞二进制中位数 1.60 MiB、最大 38.04 MiB。智能体只拿到 stripped 的漏洞与补丁二进制、运行时依赖与工具、受控受害服务，以及 1000 次调用预算；拿不到源码、源码补丁、漏洞描述、参考 PoC 或触发输入。主结果：Codex + GPT-5.6 恢复 88/100、审计通过利用 20/100、每任务 28.11 美元、2.13 小时；Claude Code + Opus 5 为 85/100 与 6/100、14.90 美元、1.26 小时；Kimi Code + K3 为 64/100 与 0/100、38.34 美元、5.80 小时。仅提供漏洞二进制时恢复率 55%，同时提供补丁二进制升至 90%、利用从 10% 升至 25% 且成本更低。对 20 个成功目标启用金丝雀、PIE、Full RELRO、NX 与 Fortify 后，恢复降至 15/20、利用仅 2/20。
支持「进化对齐脆弱性」的工程侧：补丁一旦发布就同时成为攻击说明书，「修复」行为本身制造了新的攻击窗口。恢复率 64 至 88% 与利用率 0 至 20% 的巨大落差说明瓶颈不在定位而在「理解漏洞能控制什么」——这与本书「能力可测量、后果不可测量」的区分高度一致。纵深防御有效但只挡掉九成，剩余一成足以致命。

Claude Code 被曝把密码写进项目文件，GitHub 上发现 2539 个真实凭据，官方正在修复

8.0/10
IT之家·人工智能 · 2026-11-10 · ↗ 原文 · 📍 Chapter 5, Section II
2026 年 11 月 10 日，IT之家转述 Ars Technica 与安全公司 Apiiro 的发现：超过 10 万份 Claude Code 本地设置文件被上传到公开 GitHub 仓库，其中约 1100 份含有数据库密码、API Token、私钥或 root 登录信息；结合 Git 历史、共享设置文件与智能体聊天记录，共在 1994 个代码库中识别出 2539 个真实凭据，波及 63 个组织，包括学生团队、初创公司、软件代理商与成熟供应商，泄露内容包括 Azure 数据库密码、Square 生产令牌、SSH root 登录信息乃至医疗记录数据库的拥有者密码。机制在于 Claude Code 处理「自动执行命令」授权的方式：用户在询问是否允许某条 Shell 命令时选择「是，且不再询问」，该规则连同命令原文——可能夹带密码、令牌、密钥——一并写入 .claude/settings.local.json；该文件本应被全局 .gitignore 排除，但当项目被克隆到另一台机器、或普通文件夹后来才初始化为 Git 仓库时，就可能被误提交。研究还称 Claude Code 有时会在未经确认的情况下自行提交设置文件变更，且即便原仓库删除，fork 仍会留存密钥。统计上允许列表越大风险越高：超过 8KB 的文件每十个有一个含真秘密，小于 500 字节的文件不到五百分之一。同类 bug 早在 2025 年 8 月已被报告，因 60 天无活动被关闭；Claude Code 团队的 Boris Cherny 于 11 月 7 日回应称正在研究预防措施，并考虑内置密钥扫描。
支持「需求侧规训」的代价结构：每一次「不再询问」都是用未来的安全边界换取当下的摩擦消除，而摩擦正是判断发生的位置。这同时补足「暗时间」的一条：授权决策被写入文件后不再被任何人重读，审计对象从「人」变成「配置」——没有人在场，所以没有人负责。

MEDSchneier on Security·↗ 原文·📍 Chapter 5, Section II
2026 年 11 月 10 日，Bruce Schneier 记录了一个被命名为「*sshole」的 OpenSSH 漏洞：在 Alpine Linux 及其他基于 musl 的系统上，攻击者只需提交超过 256 字节的超长密码，就能登录那些已配置为禁止密码认证的账户，即绕过「仅允许密钥登录」的加固设置。该缺陷已在代码中存在约十年，被 Schneier 评价为「很糟糕的一个」。漏洞细节发布在 sshhole.com，BleepingComputer、Slashdot 与 Ars Technica 均有报道。技术根源在于 OpenSSH 与 musl libc 在超长输入处理上的不一致，使认证失败路径被误判为成功。由于这条防线是无数「安全基线」文档的标准条款，受影响面可能远大于 Alpine 自身的装机量。
