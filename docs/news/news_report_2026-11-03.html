Scaling Git at OpenAI

9.0/10
OpenAI News · 2026-11-02 · ↗ 原文 · 📍 Chapter 8, Section II
Codex 让工程师并行改动数量远超以往，每次 push 又触发多个 CI 作业重复 fetch 同一 commit，OpenAI monorepo 的 Git 服务可靠性一度跌破 90%，2025 年底起出现 fetch/push 缓慢与 merge 失败。OpenAI 遂重建 Git 后端 Pando：与 Git 协议和客户端完全兼容，核心设计由 1 名工程师完成、Agent 团队实现、少数工程师部署，10 周上生产，2026 年 4 月起承载流量，迁移数百个集成与数百万分支。中位 push 延迟降近 80%，每日交付近 1PB Git 数据，单小时峰值 57TB+ pack、其中 99% 以上来自缓存，仅少量 CPU 核心即可支撑；push 元数据 O(1)、fetch O(log Δ)。它放弃全仓库时点一致性、改为因果一致性，只对单个 ref 串行化，理由是用户与 Agent 都不关心 ref 的全局顺序。另用 GPT-6 Astra 让 Agent 写 Lean 与 TLA+ 形式化「Pando 理论」并证明性质，连续会话数百小时找边界 bug。
直接落在 Silicon Internal Loop：模型不仅写应用代码，还开始重写自己运行所依赖的基础设施，且设计、实现、验证三环节出现「人定架构、Agent 实现、Agent 形式化验证」的分工。更值得记的是它为了让 Agent 负载跑通而主动放弃全局一致性——「用户与 Agent 都不关心 ref 全局顺序」这句话把智能体正式并入「用户」概念，等于承认系统的语义契约由 Agent 的实际行为而非人类直觉定义。

Building Legal Agents When You Can't See the Data - Jacob Lauritzen, CTO of Legora

8.0/10
Latent Space · 2026-11-02 · ↗ 原文 · 📍 Chapter 3, Section IV
Latent Space 11-02 播出 Legora CTO Jacob Lauritzen 访谈。Legora 的智能体为律所处理起草、万份合同表格化审阅与尽职调查，但公司读不到任何一条 trace——数据属于律所客户。其做法是三名工程师加三名律师，按客户真实工作搭建模拟测试「世界」，类似强化学习环境；无法看原始轨迹时改为转述轨迹，并把失败归并成十到二十类。Lauritzen 估计模型已能把约 60% 的法律工作做好，其余需要更强模型。一个细节：某次引用准确率从 70% 跳到 99%，而 Legora 什么都没改，是模型换代带来的。公司曾长期拒绝做模型选择器，后因客户需求加入；全部跑在 Azure；现有 100 名法律工程师，而他当年用「300 斯巴达」幻灯片论证 20 人永远够用。另谈及计费小时制与初级律师去向。
暗时间的供应商版本——不仅用户看不到过程，连造它的人也看不到。更尖锐的是那个 70%→99%：质量跃升来自外部模型换代而非自身工程，意味着产品能力的因果链落在供应商视野之外。他们能做的只有把失败归类、把测试世界造得像客户的工作，用间接信号替代直接观察——这正是暗时间在产业链上的传导方式。

腾讯混元发布 Hyra 2.0：让通用 agent 研发可复用的科学工具与模型

8.0/10
公众号：腾讯混元 · 2026-11-02 · ↗ 原文 · 📍 Chapter 6, Section II
腾讯混元 11-02 发布 AI 科研系统 Hyra 2.0，把重点从「用 AI 直接解题」转向「让通用 Agent 参与研发科学模型、研究工作流与软件工具」，使一次研发成果可在后续任务中反复使用，官方称之为从「刷题解题」走向「造工具」、形成「智能复利」。架构分三层：Overall 与人类研究者沟通并对齐目标，Mission 长期负责单一研究问题并判断路线取舍，Worker 独立读代码、做实验、分析失败原因，并可质疑 Mission 的判断。系统另设三套分离存储：项目状态、Agent 分层记忆、共享知识库 Books；项目复盘时可把可迁移方法整理成 skill 供后续任务直接调用。此前 Hyra 1.0 曾驱动开源模型解决加法组合学中悬置五十余年的开放问题。
丰裕闭环的工程形态。关键不在解题而在把解法沉淀为可复用工具，于是单次投入的收益随任务数摊薄——这与「每次从零推理」的调用式 AI 是两种经济结构。Worker 可质疑 Mission 这一设计尤其值得记：层级里内置了向上反驳的通道，是对「对齐即服从」的一次结构性偏离。
